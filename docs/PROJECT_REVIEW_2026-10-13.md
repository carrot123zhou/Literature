## 2. 优先处理的发现

P1 表示影响成本、数据保留或成品正确性的主流程问题；P2 表示性能、质量能力与工程完整性改进。复现数字只来自合成样例，不代表真实大书的速度或费用。

### R01 / P1：翻译启动的项目互斥存在竞态（已复现）

位置：`literature/api.py:468`，`JobManager.start_translation`。

当前实现先查询已有 queued/running 作业，再独立创建任务，没有锁或数据库唯一约束覆盖整段操作。两个并发请求都可能查到“没有活动任务”。隔离测试用 Barrier 让两次查询同时结束，结果创建 **2 个 job、提交 2 个 worker**。

影响：同一项目可重复调用模型；译文提交锁只保护最终写入，不能防止此前重复生成和费用。现有 `test_translation_job_rejects_concurrent_start` 只验证已有作业时的串行拒绝。

建议：项目级原子领取/创建（新建与 resume 共用），加请求幂等键；结构任务也需要明确重复启动策略。验收：并发新建、新建与 resume、重复 resume 均只允许一次领取和一次模型调用。

### R02 / P1：checkpoint 写入晚于阶段执行，崩溃恢复会重复翻译（已复现）

位置：`translation.py:638`、`804`、`968`。

`run` 在初译/润色阶段返回后才保存 checkpoint；分块提交只保存 translation.json。平稳暂停会经过阶段收尾，现有测试覆盖了它；进程中断可能没有经过收尾。

隔离样例：6 个独立分块、单路强制重译，前 5 个完成并触发写盘，第 6 个通过 BaseException 模拟绕过正常收尾。磁盘已有 **5 个译文条目，但没有 checkpoint**。同 job 恢复后发送 **6 次请求，重复处理之前的 5 块**。这验证的是收尾被跳过的崩溃边界，不是一次真实杀进程验收。

建议：首次请求前冻结 target_ids、源 hash、pass、模型非敏感配置与术语表版本；每次有效结果提交后持久化完成清单。提交和 checkpoint 的跨文件崩溃窗口需通过提交日志/可恢复事务处理；至少避免已经持久化的结果再次进入 force 请求。未获得响应的在途请求标“结果未知”，不能承诺从未计费。

### R03 / P1：导出漏掉图表附注和表格标题（已复现）

位置：`exporters.py:114`、`206`、`349`。

规范化和翻译引擎保留 `caption`、`footnote` 字段，导出器却没有统一覆盖它们。合成图片块与表格块中，图片附注、表格标题、表格附注在 **Markdown 与 HTML 输出中全部缺失**；EPUB 的正文共用 HTML 渲染，因此共享该问题。DOCX 对表格分支仅写 cells，对图片仅写 caption，也存在对应字段缺口（代码确认）。MD+JSON 中 JSON 仍保留字段，不能据此认为其 Markdown 已完整。

建议：建立全格式共用的字段遍历契约：正文、列表、图题、表题、块附注、独立页脚注、cell、资源，每种支持原文/译文/双语。验收使用每字段唯一标记，逐格式检查实际成品出现，不能只断言“文件生成成功”。引用回流属于另外的能力，需要单独验收。

### R04 / P1：部分解析被导出预检误报为完整（已复现）

位置：`exporters.py:400`、`frontend/src/workbench/ExportPanel.tsx`。

`export_readiness` 只检查 canonical 中当前存在的块，不检查 document.coverage。合成项目标注 **partial 50/359 页**，当前可译块全译后预检返回 **ready=true**；前端因此显示“全部内容已完整翻译，资源齐全”。资源页已经区分部分解析，导出页未沿用这个口径。

建议：同时返回源页覆盖、已解析内容翻译覆盖、资源/字段完整性。未知覆盖也不能称全书完整。仍允许知情导出部分内容，文案与报告明确“已解析 50/359 页”。

### R05 / P1：不同语言导出使用相同路径，会覆盖此前成品（已复现）

位置：`exporters.py:242`、`262`、`283`、`349`。

路径包含 title 与 mode，没有 locale。先导出 zh-CN MD+JSON，再导出 ja，**两个目录相同，先前 translation.json 被替换为 ja 层**。EPUB/DOCX 与 HTML 采用同类命名。项目库译文层不会因此丢失，但已导出成品被覆盖。

建议：文件/目录包含 locale 与导出版本，报告记录源/译文修订；先在临时目录生成所选格式，验证成功再发布，避免导出失败留下看似成功的半套成品。

### R06 / P1：表格 rowspan 坐标与 DOCX 合并单元格不完整（已复现）

位置：`mineru.py:90`、`exporters.py:349`。

HTML 表格解析器每行将 column 归零，没有跳过上一行 rowspan 已占的列。样例首行 A rowspan=2、B，第二行 C：实际 canonical 把 C 放在 **(1,0)**，正确位置应为 **(1,1)**。这会影响阅读和导出；raw 证据仍保留，可据此重建，但旧 cell ID 的迁移必须谨慎。

另一个样例首行 colspan=2，导出的 DOCX 第一格没有 `gridSpan`，证明 exporter 未执行合并。HTML 已输出 span 属性，不能替代 DOCX 验收。

建议：规范化时维护占用网格，导出器统一消费准确坐标与跨度；DOCX 按跨度 merge。旧数据修复明确映射现有 cell ID 与译文，不能静默换 ID。

### R07 / P1：译文历史递归复制，体积快速增长（已复现）

位置：`translation.py:1424`、`1547`。

重译和人工编辑均执行 `revisions.append(asdict(previous))`，previous 自带完整 revisions。新版本既保留历史列表，又在快照中再次嵌入它。同一短段编辑 1 / 5 / 10 次，translation.json 分别为 **699 / 11012 / 446645 字节**，是重复嵌套造成的快速增长，不是正常每次多一个短版本。

影响：整层读取、序列化、写盘、前端轮询都会放大；候选中完整条目快照也需检查。

建议：保存平面内容快照，去掉 revisions/candidates 等历史容器；更长期可把版本放 SQLite 或追加日志，以 ID 引用。验收几十次重译/编辑后体积随版本数近似线性增长，旧版本仍可审阅。

### R08 / P1：超长单段不受分块预算约束，且不能再拆（已复现）

位置：`translation.py:442`、`465`。

2400 字符和 12 字段预算只在 block 之间分包。单段 10000 字符仍作为一个请求，`_split_units` 对只有一个字段返回无法切分。超大表格也可能初次超出字段预算，只在响应失败后拆字段。

建议：按预估 token、字段数和输出容量预拆请求。超长字段使用临时 subsegment ID、句子边界和明确拼接规则，最终仍回挂稳定 block/cell ID；不要更改 canonical 身份。验收包含长段、超大表格、公式与引用跨边界、拼接完整性。

### R09 / P2：费用预估与预算控制覆盖不足（代码确认）

位置：`translation.py:551`、`961`、`providers.py:315` 附近、`api.py` 的 TranslationEstimateInput。

预估仅按 source_chars/2 计算输入、输出；不计每请求 system prompt、前后文、术语、协议标签、自动 polish、force 重译，输出 token 也直接等于输入。这里既可能低估，也可能高估，不能当硬报价。

预算只检查已记 estimated_cost，没有预留在途请求、内部切分子请求和退避重试的费用。无单价时费用未知，也不能承诺硬上限。cached_tokens 已记录但未设缓存单价，成本计算未区分缓存计价；缺失 usage 与超时后的未知费用也应独立表达。

建议：预检复用实际分块/输入构造，按语言与模型计数能力给出区间；同时预留在途费用并在响应后对账。每个外部请求（包括 retry、结构、即时翻译）统一进入预算与用量管理。缓存计价应按具体服务支持与价目配置验证后启用，不能套用通用折扣。

### R10 / P2：资源页重复扫描已形成明显二次增长（已测量）

位置：`storage.py:174`、`api.py:689`、`ocr.py:265`。

`project_path` 每次查 ID 都扫描所有 `project.json`；`/projects` 又逐项目读取作业、校对与覆盖。合成无 canonical 项目，单次请求的 project.json 读取次数：**10 项目=305；50 项目=6525**。两次请求均 200。该数字是文件读取次数，不是耗时基准；有规范文档时还会增加解析与统计。

OCR 列表也遍历历史作业、逐作业加载项目；任务历史归档主要是展示元数据，不能将“归档”误认为消除了扫描或释放了 raw 空间。

建议：内存 project_id→路径索引（创建/重命名/删除失效）、单次请求内复用上下文、持久化轻量阶段摘要；资源页后端分页/搜索，任务历史先按元数据筛选再加载明细。索引可重建，不能取代原件与 canonical 事实来源。

### R11 / P2：轮询传输过重，暂停时仍拉整层（代码确认）

位置：`frontend/src/App.tsx:55,105,116,126`、`ProjectLibrary.tsx:231`。

当前项目每约 1.5 秒拉详情，包含完整 jobs 与 result/audit；paused/budget_paused 也被列为 active 并拉整层译文。资源页同时每 3 秒拉 projects、每 2 秒拉 OCR jobs，保留最近项目后项目详情轮询仍运行。结构审计保存了完整模型请求/响应，详情随历史增长会越来越大。

初次 refreshProject 的独立读取按顺序 await，可并行；旧请求的写回只校验 project_id，语言快速切换的响应也应按请求代次/locale 校验。阅读页和结构结果页均 map 全部 blocks，阅读条目没有窗口虚拟化，轮询会扩大重渲染成本。

建议：轻量状态与详细审计分接口；ETag/revision + 条目增量、按页面/任务状态调整刷新，闲置/暂停降频。已有 `/events` 可作为起点，但它内部仍每秒扫描，需先接入状态变更通知，不能仅换成 SSE 就称成本消失。UI 使用可变高度窗口化并保留跳转/选择行为。

### R12 / P2：质量校验偏重协议，语义与状态证据不足（代码确认）

位置：`translation.py:371,1272,1286`、`storage.py:777`、`structure_reasoning.py`。

- 翻译已检查缺字段、空输出、重复 ID、源 hash 和 length；这些证明协议完整，不能证明没有漏句、误译数字、颠倒否定或术语漂移。
- polish 的字段输入主要是现有译文，缺对应原文对照；润色能改善文风，也可能改变信息，当前没有语义效果证据。
- 学术人文 prompt、专名“中译”措辞覆盖多种目标语言，代码块又同时受“都要译”和“代码保留”原则约束，应明确按文献/语言/字段制定策略。
- 默认 4 路并发不带上一块译文；串行模式才有最多 400 字的译文衔接。并发模式质量依赖术语与原文上下文。
- 原文前后文不区分章节边界；选择离散章节时可能将不相邻的块打在一起。
- 校对 done 由已有补丁或已处理建议推导，不等于完整审查；一项手改就可以 done，零建议的成功审查可能仍 todo。

建议：本地检查数字、引用、公式/URL、空字段、目标语言、术语和异常长度；可疑处进入复核，避免将启发式检查当语义判决。只对高风险段落进行带原文的译审。校对状态绑定文档版本、范围、实际覆盖和人工确认，允许“已检查、无需修改”。

## 3. 每个模块如何运行

### 3.1 macOS 客户端与本地服务

入口：`src-tauri/src/lib.rs`、`literature/sidecar.py`、`literature/api.py`、`frontend/src/api.ts`、`desktop.ts`。

1. Tauri 单实例启动并选择资源库，准备 runtime/logs。
2. 获取动态 loopback 端口，生成随机会话 token，启动内置 Python sidecar；环境变量传入库路径、端口和 App PID。
3. React 从 runtime_info 得到地址和 token，等待健康/能力检查，API 请求携带 `x-literature-token`。
4. FastAPI 初始化 ProjectStore、MinerUService、JobManager、模型服务和上传暂存；启动时处理遗留作业并恢复 OCR。
5. 退出时清理 sidecar 进程组；后端另有 App PID watchdog。

打包路径：`scripts/build_sidecar.py` 的 PyInstaller onefile → `src-tauri/binaries` + 哈希清单 → Vite 前端/PDF 解码资源 → Tauri app。发布态不依赖用户 Python/Node/Vite。现有包主要是 Apple Silicon、adhoc 签名；公证、Intel/干净机等不能由源码检查替代。

优化：记录启动耗时后再比较 onefile 解压与目录型 sidecar；按页面懒加载代码与 PDF 模块；固定支持的 Node/Python 构建环境。开发环境版本告警不意味着打包后的客户端运行依赖 Node。

### 3.2 文件导入、任务首页与资源管理

入口：`ImportWorkspace.tsx`、`ProjectLibrary.tsx`、`TaskHistory.tsx`；后端 `uploads.py`、`api.py`、`storage.py`、`task_history.py`。

桌面原生选择/拖入本地路径 → inspect 元数据 → 逐文件页码/额外格式设置 → 项目原件副本 + 任务参数快照 → 入解析队列。浏览器调试通过 multipart 暂存接到同一后续流程。源文件命名为 `origin.<扩展名>`，创建时记录 hash。

资源页聚合解析、校对、翻译、导出四个维度；历史任务与长期文献资源分开。归档只影响任务展示，项目删除移动到 `.trash`。首次解析、继续未覆盖页、失败切片重试分别使用不同操作。

优化：R10/R11；重复源 hash 先提示已有资源，允许不同解析参数创建独立项目；暂存只清无引用且过期的文件；增加可见回收站恢复。不要将 raw 或用户译文视为缓存删除。

### 3.3 MinerU 调度、切片、恢复

入口：`ocr.py`、`parse_queue.py`、`mineru_workflow.py`。

1. 验证 Token、源存在/hash、项目活动任务及状态；新路径使用 schedule→project/job 锁。
2. PDF 按页数/大小切片。指定页码先本地提取子集，切片保存 source_pages 映射，避免远端 page_ranges 语义歧义。
3. 队列默认单文档串行、可调序且不抢占；一份文档可向远端批量提交多个切片。
4. 请求上传 URL → 上传 → 按 data_id 匹配轮询结果 → 下载续传/刷新地址 → 安全解包与页数校验。
5. 所有需要的切片下载后按源页合并。任务完成与全文覆盖分开；继续解析只补未合并源页。
6. 重启恢复轮询/下载；失败切片重试保留成功结果。远端没有真实暂停/取消，客户端退出不能假定远端已停止计费或计算。

优化：先测本地准备、上传、远端等待、下载、合并的分阶段耗时，再决定哪一段需要并发。上传/下载可考虑有限并行，但不能损坏持久化与证据封存。轮询按远端阶段与退避调频。解析参数应按实际文献需要配置，效果依赖真实样本。

### 3.4 规范化、文档图谱与存储

入口：`mineru.py`、`models.py`、`storage.py`。

content_list_v2 优先，兼容旧 content_list/Markdown；提取文本、列表、表格 cell、标题、图片、脚注、bbox、页几何，保留 raw 字段。资源按内容 hash 去重到 assets。canonical 使用源文件页号；首次生成稳定 block ID，追加页生成独立 ID，旧 ID/人工修订/译文挂接保留。标题栈生成 toc。

raw 复制/哈希/封存清单属于证据；document.json 属于长期主数据；source.md 是可读投影。SQLite 保存作业、修订、建议决策与用量；译文按 locale 保存独立 JSON。各写入者使用文档、raw、译文锁。

优化：R06/R07/R10。Document.block 等查找可有运行期索引；缓存以 revision/mtime 失效。结构补丁保存 document→source.md→SQLite 顺序并不等于跨文件数据库事务，应加恢复日志与故障注入验证，保证不会出现改了文档却无撤销记录。JSON 原子 replace 只防半文件，不能代替业务事务。

### 3.5 原页阅读与人工结构编辑

入口：`frontend/src/review/` 的 ReviewWorkspace、SourcePreview、PdfPane、PdfPageCanvas、ResultPane、OutlinePane；后端 `structure.py`。

目录/块/原页 bbox 共享 active block。PDF 单文档加载，当前页前后窗口渲染 canvas，其余页占位；bbox 根据 0–1000 坐标叠加。选择结构类型或 H1–H6 → 服务端校验原状态 → 修改 canonical/toc → 保存补丁。撤销按后续修订顺序拒绝陈旧覆盖。非 PDF 使用图片/HTML或明确降级预览。

优化：PDF 已有渲染窗口，重点是块列表窗口化、页高前缀和/定位索引、重渲染范围与原页解码回归；不要再为全部 PDF 页面同时渲染 canvas。验收断言实际像素和文字可見，不能只检查容器存在。

### 3.6 结构 AI 校准

入口：`structure.py`、`structure_signals.py`、`structure_reasoning.py`。

本地：目录候选、重复页眉/题注/几何/编号信号 → 有序目录对账 → 可逆建议；可信本地自动操作有独立阈值和白名单。

AI：用户所选目录页/确认目录 → 可选图像证据（最多 6 页目录与 6 个代表性裁片） → 模型核对目录 → 每窗口最多 64 候选的整体标题树规划 → 每批 40 候选的角色复核 → 阅读顺序下父子关系检查 → 待人工采用建议。

普通正文不全文发送，但疑似漏标短正文会进入候选，这两者要在输入审计中区分。现有标题全部参与 AI 审查，本地匹配只是线索，当前 AI 路径并非“只发送疑难项”。每轮请求记录输入、耗时、响应、usage；失败任务同文档/配置/请求可复用已有响应。

效率：例如 231 个候选且执行目录提取，正常约 **1+ceil(231/64)+ceil(231/40)=11 次模型请求**，不含拆批和重试。每轮规划会重复完整目录与最多 48 条 overview，候选也经历规划/复核两轮，这是质量设计的成本。

建议：已确认目录没有变化时复用确认基准；缓存本地信号/裁片；用内容与请求 hash 细化缓存，不仅依赖整份文档 updated_at。保留全量审查模式，再用评测决定增量规划、疑难复核或单轮模式是否可提供。模型置信度不能直接授权自动采用，也不能证明无需第二轮。

### 3.7 翻译、术语、人工编辑与恢复

入口：`translation.py`、`api.py`；前端 ReadingWorkspace、ReadingPanels、ReadingBlockCard、GlossaryEditor。

1. 选择全书、未译、待复核、失败或章节/block；加载目标 locale 的译文层和术语表。
2. 跳过人工锁定；纯结构层级变化更新依据版本而不重译；原文 hash 变化才需要重新生成。
3. 默认 2400 字符/12 字段分块，前文最多 700、后文最多 500 字符；默认 4 路并发，上限 8。
4. 原文组织成 `<src id="block#field">`；模型输出 `<seg>`；按 text/item/caption/footnote/cell 验证。
5. 缺失或截断响应进行有界字段拆分，子请求错误隔离；部分块成功可保存，失败块保留原因/候选。
6. 主线程记 usage 与合并结果，约每 5 块或 3 秒提交整层。提交时保留运行期间人工编辑，源文已变的 AI 结果只作候选。
7. 可选全量 polish，再保存 checkpoint 和终态。暂停在分块边界生效，已发请求需结算。
8. 手工按字段编辑自动锁定；划选只浮出按钮，点击才即时翻译，附属选段记录不替换整个块。

优化：先 R01/R02/R07/R08/R09。按语言/章节边界组织分块，正文和大表分策略；冻结章节术语/风格/文献类型的短上下文，实测上下文长度的价值。成功字段复用要记录 source hash、prompt/model/术语版本和验证状态；未校验候选不得冒充成功复用。

最大输入开销之一是重复提示和上下文：2400 字符正文配满 1200 字符前后文，单就原文字符占正文的 **50%**；12 字段限制导致更短请求时占比更高。该比例不是 token 或费用实测。不能因此删掉所有上下文，应比较 400/200、700/500 与章节短摘要方案的成本和质量。

### 3.8 模型服务、连接与用量账本

入口：`providers.py`、`model_services.py`、`frontend/src/modelServices.ts`、ModelServicesDialog。

服务库保存 URL/model/温度/输出上限/单价，密钥放 Keychain；结构和翻译按角色绑定。OpenAI-compatible provider 复用 httpx.Client 连接，对部分 429/5xx 等状态退避；超时不自动重发。usage 记录实际服务返回的 input/output/cached/reasoning token 与请求 ID，费用按用户配置单价估算。

优化：所有项目、结构、翻译、即时请求共用服务级并发/速率额度；当前一个后台 job 可开 4–8 路，JobManager 还允许两个后台作业，不能只看单本书并发。429 时共享冷却、加抖动；持续故障熔断需覆盖“前面有成功、后面持续失败”，当前 success_blocks==0 才全局中止。

job 配置通常存 service_id，恢复时再读取可变服务配置，模型/URL/术语可能不同于首次运行；应冻结非敏感参数与版本。provider.close 已定义，AI 主要任务结束路径未显式调用，建议 finally 释放，清理 pause_events 和已结束任务句柄。结构失败也应统一保留已有响应 usage，不能因空内容异常漏账。

### 3.9 导出与外部 TBL

入口：`exporters.py`、ExportPanel、`tbl.py`。

从 canonical + locale 译文 + assets 生成原文/译文/双语 HTML、MD+JSON、EPUB、DOCX。导出检查 failed/partial/source hash/缺字段，缺译明确标记；四种格式目前各自加载快照。EPUB 划 H1/H2 章节并生成 nav，验证 ZIP 必需项与 XML 可解析。TBL 接收派生 EPUB/DOCX，结果不回写 block 图谱。

优化：先 R03–R06；一次 export_all 读取同一文档/译文快照并共享字段遍历，避免多格式间读到不同版本；EPUB 目录依据嵌套 toc 与稳定锚点，纯译文目录使用译后标题；验证内部引用、资源/媒体类型、脚注及阅读器实际渲染。需要完整 EPUB 标准验收时另加专门验证器，现有 validate_epub 只能证明基本包结构和 XML。

## 4. 效率、token 与质量优化的实施顺序

| 顺序 | 交付目标 | 主要改动 | 验收依据 |
| --- | --- | --- | --- |
| 1 | 同一内容少付重复费用、成品不丢信息 | 原子启动与幂等、请求前/分块 checkpoint、导出字段/覆盖/语言路径、平面版本历史 | R01–R08 的隔离场景转为有业务断言的回归；并发只一次调用；恢复不重发已持久化结果 |
| 2 | 看见时间和钱具体花在哪 | 实际请求预检、预算预留、用量未知状态、分阶段耗时/首响应/重试记录 | 原始响应 usage 可对账；初译/润色/重试费用分别可见；价格未知不显示零成本 |
| 3 | 减少本地等待和重复读写 | 项目索引、轻量/增量状态、块窗口化、同一导出快照、provider 生命周期 | 100/1000 项目读取与 p50/p95；500 页滚动/内存；暂停和闲置停止整层刷新 |
| 4 | 用更少输入获得稳定译文 | token/字段/章节分块、长字段临时子段、可验证字段复用、上下文消融、裁片/请求缓存 | 总输入/输出/缓存/reasoning token 每千源字；成功字段重复率；术语/漏译评测不退步 |
| 5 | 只把复核成本花在问题段 | 本地规则告警 + 带原文定向译审、结构增量候选与全量模式对照 | 数字/否定/引用/脚注完整性；标题角色/层级/父子关系；人工修改量与模型费用共同评估 |

真实评测建议使用已许可的小规模代表样本，覆盖长段、跨章、表格、脚注、复杂标题树；冻结源数据和术语，不默认发送整本私人文献。基线选择当前 v2，分别比较分块、上下文、并发、是否定向复核；保持其他变量一致。记录漏译/数字引用保持率、术语一致率、标题准确率和人工修订量，而非仅计算模型“成功返回率”。

本轮没有真实 provider 速度/质量/费用数据，所以不承诺具体节省百分比，也不据模拟响应推荐某个当前商业模型。优先落地能从代码与复现明确验证的重复成本和质量缺口。
