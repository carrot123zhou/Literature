## AI 速度、质量与数据传输

### 调度策略

现有 v2 的小块、长连接、4 路并发、术语过滤和局部重试方向合理，真实收益尚未测量。不要把默认并发继续拉高作为主要优化。

1. 以 token 预算而非固定字符数打包，受输入上下文、预期输出、字段数量和 provider 能力约束；按章节/语言边界切块。超长单段当前仍整段发送，且只有一个 segment 时无法再次切分：新增临时子段 ID 与可追踪拼接，保持 canonical block ID 不变。
2. 所有项目、结构作业、即时翻译共用 provider 级调度器；按延迟、429、失败率调节并发，限制 RPM/TPM，并给交互请求保留容量。单项目互斥不能代替全局额度控制。
3. 发送前预留预计费用，完成后按 usage 对账。现在只检查已记费用，多个在途请求可超过预算；没有价格时不能将未知费用当作零成本或承诺硬预算。
4. 429/5xx 使用全局冷却和抖动；鉴权/不守协议等错误先停止继续入队。当前熔断仅在总成功数为零时生效，一旦有成功后持续失败仍可能遍历余下分块。
5. 每个请求记录排队/发送/首响应/完成/重试时间、token、请求 ID、终止原因与结果校验。流式预览有助于感知，但只将已校验字段保存为正式译文，不能把 token 流误认成完成。

### 质量策略

- 并行翻译共享冻结术语表、文献类型和简短章节摘要；相邻原文上下文继续保留。当前只有串行模式使用上一块译文，因此并行下术语与语气连贯要单独评估。
- “初译→校验→有问题的段落定向复核”优先于全书两遍文学润色。当前润色主要输入初译，缺相应原文，不足以保证事实忠实；译审应同时看原文和译文。
- 提供少量产品预设：学术忠实、流畅阅读等，说明成本和取舍。不要承诺开启润色必然提升质量，也不要把并发 8 标成“最快”。
- 专名处理应按目标语言和学科统一，现有提示中的“一律中译”“文学编辑”对多语言/学术材料并不完全匹配；给用户展示少量代表样本后冻结偏好。
- 翻译提交日志与结果 checkpoint 原子关联；成功结果缓存键包含源 hash、语言、模型配置、prompt 版本、术语快照和上下文版本。仅同一任务重试默认复用；明确“强制重译”需重新生成。
- 避免嵌套完整 revisions 导致历史反复复制；改成独立版本记录与引用，translation.json 仍保留为正式、可迁移的投影。

### 两段数据传输分别优化

应用↔本地后端：首次加载规范文档，后续接收状态与条目增量；项目摘要不要重复加载整书。可先实现 revision/ETag+自适应轮询，再按实际收益采用 SSE。现有认证使用会话令牌，事件通道需保持认证边界；不能直接照搬无鉴权 EventSource。

后端↔外部服务：继续保留结构校对有界候选与视觉裁片、模型输入审计、长连接和术语过滤。结构语义质量依赖全局目录与父子上下文，不能为了速度回退到仅凭本地编号判断；只对确定未变的阶段做缓存复用。

## 将用户置于处理循环中

以“选择目标→查看处理计划→启动→持续看到结果→仅处理疑点→查看交付报告”组织交互。目标可以是只提取、校对原文、获取译本或制作双语阅读稿，底层仍使用独立任务组合。

启动前展示实际发送的范围、目标语言、服务与估价；首次外发的确认可包含本次后续步骤，减少每批重复打断。自动化只继续用户已选定的目标，不擅自把新导入文档全文发送给翻译服务。

运行中常驻显示正在执行什么、完成多少内容、失败/待确认数量、最近活动、暂停请求与生效状态。ETA 基于近期真实耗时给区间，信息不足时显示已运行时间。网络错误保留在页面，不能只显示短暂 toast 或吞掉错误。

用户介入点：术语/风格样本确认、结构修改确认、可疑译段处理、导出不完整内容的选择。已有自动应用边界继续生效：高置信本地可逆修改才允许按规则自动采用，AI 自报 confidence 不授权自动修改。

状态契约至少区分：任务 queued/running/pause_requested/paused/partial_failed/failed/completed/interrupted；内容 untranslated/translated/locked/needs_review；交付 draft/validated。独立维度可以并存。应用重启后明确“中断、已保留 N 段、可继续”，避免把中断等同于模型错误；默认不重新发送状态未知、可能已计费的请求。

## 建议执行顺序与验收

第一轮：F01–F05 翻译完整性与提交安全，F06 语言与导出完整性，F08/F09 编辑保护和即时翻译确认。交付一个可信的小样端到端链路。每个缺陷配对应边界测试，不能只检查 job completed。

第二轮：provider 全局调度、token 分块、请求/字段 checkpoint、增量状态、术语与质量复核。用同一代表样本比较当前 v2 与优化版，记录总耗时、每千原文字符费用、请求/重试数、漏字段、术语偏差和盲审质量；只有真实结果支持才宣称提速/提质。

第三轮：统一翻译入口、处理目标预设、异常驱动复核、F07 导出资源契约、回收站、客户端正式验收和大库性能。避免先做大规模架构重写。

建议首批验收矩阵：短文本 PDF、500+ 页扫描 PDF、图片、DOCX、PPTX、XLSX、HTML；涵盖英文/日文/混合语言、无目录、多级无编号标题、跨页表格和脚注。模型使用真实兼容服务，实际调用范围与费用事先明确。所有结果按“已编码/自动测试/隔离联调/真实服务/原生客户端”分别记录。

首轮硬指标：人工编辑丢失 0；通过完整性校验的条目缺字段 0；空输出误判完成 0；纯层级变化新增翻译请求 0；暂停润色误报完成 0；选择文字自动发请求 0；导出语言匹配 100%。大库和速度指标先建立基线，不凭经验许诺倍数。

## 官方资料核对

- SQLite 支持事务，但同时只有一个写事务；采用单写入提交与版本校验时仍须设计锁与冲突处理：[SQLite Transactions](https://www.sqlite.org/lang_transaction.html)。
- SSE 支持后端向页面发送事件，可用于增量进度；实际方案需适配当前会话认证与重连：[MDN Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。
- EPUBCheck 按官方 EPUB 规范检查出版物，适合作为发布验证，不能替代阅读器视觉验收：[W3C EPUBCheck](https://www.w3.org/publishing/epubcheck/)。
