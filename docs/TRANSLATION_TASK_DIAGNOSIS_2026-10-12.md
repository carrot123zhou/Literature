## 3. 已确认的软件问题

### 3.1 失败原因丢失，完成状态含糊

`TranslationService._finalize_job` 在有部分成功时将 job 记为 completed/100%，并清空 error。`_apply_outcome` 的无解析结果失败分支不持久化 outcome.failed 中的原因；`TranslationEntry` 没有常规 last_error 字段。`JobManager.start_translation` 也未给这种部分失败写异常日志。用户只能看到失败数，无法区分超时、限流、协议漏段、空响应和截断。

方案：持久化每次请求和每个失败字段的分类错误、阶段、耗时、request_id、finish_reason、usage 是否可得；任务结果保存目标/成功/失败/未处理数，前端显示“部分完成，25 段失败”，把处理进度与翻译成功比例分开。引入新终态前应同时处理前端类型、resume、项目摘要和兼容性门。

### 3.2 子请求异常使整批已成功结果丢失

`_translate_units` 递归调用左右子批没有异常隔离。任一子请求 ProviderError 会越过已解析的父批/兄弟批结果，进入 `_run_chunk` 的整批失败分支，返回空 segments/resolved。当前源码仍存在该缺口。

临时目录模拟：3 个 block 的父请求先返回第一个 block 的有效完整 `<seg>`，缺少后两个；左子请求模拟 read timeout。实际 2 次调用后 3 个 block 全部 failed，第一段有效结果没有内容或候选。这是已复现的软件问题，**不代表最近真实任务一定经过了该路径**。

方案：在每个子请求边界把异常转为该子批失败结果，合并父批与兄弟批的已验证字段。跨单元格拆分只保存候选直到整块完整；截断响应中的结果必须保持未验证，不可因另一个子批成功而升级成完整。保留 usage 与来源依据，遵守源 hash、人工锁定和提交前 canonical 校验。

### 3.3 仅按字符组批，短段批次可能有过多字段

`_chunks` 只限制源字符数；本次两个 2300 多字符请求各含 25/23 个字段。失败重试会按同样规则重新组批，未基于之前失败类型缩小批次。`_split_units` 只沿字段边界拆分，不能继续拆一个超长 text 字段。

方案：同时限制字符/token 预算与字段数。先以每批 8–12 字段作试验起点，失败重试 1–4 字段；这些是待测参数，不是已证实最优值。长 text 字段使用临时子片段 id，聚合回原 block ID，只有所有子片段完整通过才提交。不要修改 canonical 稳定 ID。缩批会增加请求数，需要通过真实样本比较成功率、耗时与费用。

### 3.4 仅思考响应的 usage 会被遗漏

Provider 在 content 为空而 reasoning_content 存在时直接抛 ProviderError，发生在 usage 解析与 ProviderResponse 返回之前。离线 FakeClient 返回 HTTP 200 + 10000 reasoning tokens + 空译文，可复现异常且没有 ProviderResponse 供任务记账。

方案：错误响应同样携带已获取的 usage/request_id/finish_reason，并按实际响应记录一次；无服务端 usage 的超时明确标为“用量未知”，不虚构 token 或零费用。译文失败与服务响应记账分开处理。

## 5. 推荐解决顺序与验收

1. 先补失败审计与明确的部分完成提示，保留已验证结果和真实 usage，避免下一次失败仍无法归因。
2. 修子请求异常隔离、按字段数组批、失败范围缩批。增加故障注入回归：父批部分成功+子批超时、兄弟批成功+另一批 429、截断父响应不得混入完整内容、表格字段不齐不得提交。
3. 增加按服务能力配置的思考开关/预算；经小样本确认中转支持后，翻译优先测试关闭思考。timeout 与实际延迟匹配；流式方案需同时设计空闲超时与总时长上限，不能只放宽等待上限。
4. 重建并停机更新客户端后，只用这些注释中的 1–3 段做受控真实验证，再重试剩余 25 段；记录成功率、耗时、reasoning 比例与用量。保留现有 590 段，不需要全书强制重译。
